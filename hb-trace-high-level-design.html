PRODUCT SYSTEMS/HB-TRACE V1
Design baseline · hosted pilot not ready
Product and architecture / V1 review

Trace every batch.
Run a more controlled shift.

HB-TRACE is a honey and beeswax traceability workspace for Humble Beeing Honey. It connects farmer and apiary sourcing to transformation, quality review, packaging and privacy-safe batch verification, while keeping a narrow set of collection work usable offline.

Single-producer V1Honey + beeswax pilotBatch / lot identityArchitecture from V1 planLocal-first foundation · hosted gates open
Read this first · the architectural bet

Capture a small set of records offline. Let the server confirm shared facts.

Staff devices durably queue approved sourcing commands and attachments. The server validates identity, quantity, role, dependencies and current state before committing traceability facts. Material transformations, quality disposition, document approval, recall and publication stay online decisions.

What is true today?

The repository has domain rules, a local transactional adapter, demo staff/public surfaces and an IndexedDB outbox foundation. Hosted PostgreSQL writes, private evidence storage and live publication remain disconnected. Local demo records are not hosted or backed up.

Repository foundation
00a / Product value

Prove where material came from, and what happened next.

The value comes from joining source records, production decisions and approved evidence into one traceable history. The interface should help staff move work forward while making holds, missing records and unsynchronized entries visible.

01 / SOURCE

Capture a receipt with its origin

Connect a purchase or harvest to a farmer, apiary, collection place, quantity, grade and later confirmation or dispute.

02 / MATERIAL

Follow lots through real work

Keep exact input contributions when honeycomb becomes honey, beeswax, residue, blended lots or packed product.

03 / QUALITY

Keep release authority explicit

Attach measurements and lab reports to the batch they describe. A failed result raises a review; an authorized person decides disposition.

04 / EVIDENCE

Find the record behind a decision

Link forms, SOP versions, claims and audit events without treating an uploaded image as proof that a batch passed.

05 / PUBLIC

Publish a safe batch story

Build public pages from one approved immutable revision, with generalized location and claims tied to approved support.

06 / RECOVERY

Make offline state legible

Show pending, sending, acknowledged, rejected and conflicted work separately. Preserve evidence until each command has an individual result.

00b / Product boundary

A focused pilot, with named limits.

The plan keeps the initial operating model deliberately narrow. These boundaries protect a useful migration seam without building platform infrastructure before a second funded need exists.

In the V1 baseline

Honey and beeswax operations

Farmers, apiaries, locations, purchase/harvest receipts, material lots, containers, transformations, allocations, measurements, holds, packaging, batch QR lookup, forms, controlled SOPs, a requirements register and downstream recall impact.

V1 scope Some local foundations exist

Explicitly later

Keep expansion out of the pilot path

Coffee and other commodities, individual jar serials, native apps, arbitrary spreadsheet mapping, OCR, a rich CMS, broad quality-management/HCM, multi-tenant SaaS, microservices, a plugin marketplace, Docker, self-hosted PostgreSQL and S3 application storage are deferred.

V2 / later

01 / Architectural decisions

A small stack, clear authority boundaries.

The V1 plan settles core product and architecture choices. Configuration still needed before hosted operations is called out separately with numbered review items.

TypeScript modular monolith

Chosen

One application codebase with web/API and a separately invoked worker. Framework-independent domain rules; route handlers and jobs call shared server use cases.

Managed services for the pilot

Chosen · settings open

Managed Node.js hosting, Supabase-hosted PostgreSQL/Auth and Sanity for approved assets/editorial content. No V1 Docker or self-hosted data services.

Review ↗

Server owns committed traceability

Invariant

Browser clients call HB-TRACE API commands. They do not write traceability records through Supabase Data API. Service credentials stay server-side.

Standard PostgreSQL and stable IDs

Portability rule

Application-generated UUIDv4 identities, reviewed SQL migrations and provider adapters preserve logical records across future database, identity, host and asset changes.

Append-only audit is not a ledger substitute

Invariant

Audit events describe who changed what and when. Material availability derives from ledger entries; outbox delivery is at least once and consumers must be idempotent.

Consent and operational basis stay distinct

Principle

Operational traceability is not automatically consent-based. Public profiles and stories are separately opt-in and withdrawable; public copy cannot rewrite operational facts.

Rules that protect the shift

Exact quantities

Decimal quantities and money carry explicit units/currency. Never use binary floating point for domain math.

No last-write-wins

Allocation, inventory, quality disposition, documents and publication require server validation and explicit conflict handling.

Corrections keep history

Committed material and financial facts use linked reversal/amendment records. Publications and controlled documents use explicit revisions.

02a / Runtime and data flow

One command path, with atomic boundaries.

Imports and workers use the same application services as the web API. They do not write business tables directly. Synchronous typed calls protect invariants that must commit together; the transactional outbox handles side effects and projections.

Authenticate

Resolve external identity to an application actor. Reload organization-scoped roles and required assurance on the server.

Validate command

Check payload schema/version, role, allowed transition, expected aggregate version, dependencies and idempotency key.

Apply domain rules

Use exact decimal quantities, allocation limits, cycle rejection and hold/disposition guards in framework-independent code.

Commit together

Write domain changes, material ledger, sync result and append-only audit in one database transaction where required.

Return per operation

Return acknowledged, rejected, conflicted or dependency-pending with a stable error and safe next step.

Queue side effects

Use an outbox for asset checks, exports, notifications and projection work; make every delivery idempotent.

Verify bytes

Worker checks type, size, decodability and malware status, preserves original bytes and records SHA-256 metadata.

Publish revision

Quality-authorized approval snapshots only whitelisted facts and exact approved content revisions for public reads.

04 / Traceability model

Source records flow through allocated material lots.

Direct input/output allocation edges are the lineage source of truth. Recursive queries calculate indirect ancestry and downstream impact. Public storytelling is a separately approved projection of operational facts.

Core domain / direct lineage relationshipsArrows indicate source-to-derived relationship
source / receiptmaterial / transformationsevidence / recordapproved public data

Exact direct allocations

A transformation records every source lot, allocated quantity, output lot, operator, facility and event time. Source allocations cannot exceed available quantity.

Availability is computed

Produced, reserved, allocated, discarded, packaged and reversal ledger entries determine current stock. A cached balance must reconcile to the ledger.

Quality decisions do not infer blame

A failed test flags a batch for investigation. It does not automatically assign fault to a farmer, apiary or region.

05 / Core journeys

The same history serves sourcing, production and verification.

The happy path joins collection, material transformation, quality release and publication. Each stage has its own record, actor and decision; no single screen or scan should imply that a later approval happened.

Register source

Select/create farmer, apiary and origin. Import review catches duplicates before commit.

Capture purchase

Record source type, date, grade, exact quantity, price/payment context and operator.

Issue receipt

Give a non-sensitive transaction reference; capture confirmation, unavailable response or linked dispute.

Identify source lot

Assign permanent application ID and QR, or an offline fallback code linked to the same identity later.

Extract / allocate

Commit exact honeycomb inputs into one or more honey and beeswax lots, with residue/waste where applicable.

Inspect and decide

Attach measurements and lab evidence. An authorized quality manager holds, releases, rejects or requests more work.

Package a batch

Connect released source lots to product, pack format, quantity and an external lot code.

Publish approved facts

Create a public-code mapping and immutable revision only after quality, claims and privacy approval.

A transport success is not a command acknowledgement.

A locally saved command remains provisional until its own operation ID receives a server result. Retried envelopes are safe only when the operation ID and deterministic payload hash match.

08 / Requirements and acceptance shape

What the pilot must prove, and what “ready” means.

Requirements are grouped by operational outcome. Acceptance needs source records, device evidence and named human approvals, not just a successful build or green dashboard.

Functional / material integrity

Capture all trace edges

At least 100 farmers and 100 apiaries; 600 valid purchase/harvest records across one operating cycle; multiple outputs, partial allocations, blending and later QR assignment preserve IDs and exact remaining quantity.

Functional / quality

Every release has evidence

Required processing, quality, disposition and packaging evidence exist. A superseded test or upstream hold identifies all affected downstream lots and public revisions.

Functional / public

One immutable approved revision

Every factual stage/claim resolves to approved support; withdrawn profile consent affects active/future publication without breaking operational lineage or historical audit.

Functional / operations

Evidence retrieval works

At least 50 reviewer-approved evidence packs validate against a versioned pilot export contract. Forms print on actual A4 equipment and remain retrievable with page order intact.

Integrity / synchronization

No duplicate or silent loss

Retries/reordering create no duplicate domain records. Every user-visible save is durable locally or on server. Conflicts and rejected commands remain visible and actionable.

Security / privacy

Keep private evidence private

Authorization is server-side; no service credential reaches the browser; private evidence requires current authorization and unexpired signed retrieval; staff routes have no third-party analytics.

10 / Delivery sequence

Retire high-risk decisions before increasing scope.

Security, integrity and restore evidence are gates throughout delivery, not a final hardening phase. If an offline, private-asset or lineage proof fails its agreed safety threshold, reduce scope or stop.

Phase 0 · Decide / prove

Scope and risk retirement

  • Name owners and pilot budget/timebox.
  • Approve standards, data policy and provider configuration.
  • Test target phones, printers, private assets and restore.
Phase 1 · Online skeleton

One trace end to end

  • Auth/RBAC, PostgreSQL, audit, adapters and jobs.
  • Farmer → receipt → extraction → quality → packaging → revision.
  • Trace, import and synthetic recall drill.
Phase 2 · Restricted offline

Collection commands only

  • Versioned envelope, dependency and conflict queue.
  • Fallback label, offline receipt wording and bounded photos.
  • Old-client, quota and reconnect tests on target phones.
Phase 3 · Quality / evidence

Run controlled operations

  • Blending, test attachments, impact and recall.
  • Forms/SOP versions and private evidence review.
  • Claims/story after privacy and fact tests pass.
Phase 4 · Pilot acceptance

Parallel run and cutover

  • Import agreed data and train staff.
  • Restore, recall, permission, outage and printer drills.
  • Named go/no-go, rollback and support ownership.

11 / Risks and review gates

The hard parts stay visible and testable.

The current code has a useful local foundation, but a hosted pilot needs provider, device, privacy, restore and operational evidence. No green local demo should be mistaken for that evidence.

RISK 01 / LINEAGE

Concurrent allocation or correction

Lock affected source rows or use serializable full-command retry; recheck versions/organization ownership and commit ledger, trace edges and audit together.

Domain rule exists · hosted transaction open
RISK 02 / OFFLINE

Browser storage, device loss and old clients

Prove persistence, quota warnings, app restart, unsynced recovery, session age, schema migrations and compatibility with actual supported devices.

Device proof open
RISK 03 / EVIDENCE

Private bytes and signed delivery

Private visibility from first upload, server authorization, signed URL expiry, export, retention and reconciliation must all pass before production evidence is accepted.

Provider gate open
RISK 04 / QUALITY

Standards, laboratory rules and authority

Unreviewed limits, incomplete requirements or unclear owners can create unsafe release decisions. A file upload never releases a batch.

Quality-owner gate open
RISK 05 / PRIVACY

Public content leaks operational identity

Whitelisted immutable projection, generalized geography, separately approved claims/profile, neutral lookup failures, rate limits and withdrawal behavior.

Policy and hosted proof open
RISK 06 / RECOVERY

Restore does not restore every fact

Reconcile database, Sanity documents/assets, page order, links and SHA-256 manifest. Define numeric RPO/RTO and demonstrate an isolated restore.

Targets and drill open
RISK 07 / CUTOVER

Shadow and live actions collide

Assign exactly one system/operator to live kitchen dispatch, payment collection and fiscal documents; define rollback and shift reconciliation first.

Operational procedure open
RISK 08 / SUPPORT

Failures have no named owner

Staff need sync remediation, support escalation and safe stop/reopen rules. A heartbeat is not authorization to resume after a failure.
